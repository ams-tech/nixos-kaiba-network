01 / What runs today

One live probe. One complete ceremony simulation.

The read-only probe remains the only hardware-backed slice. The interface now rehearses the complete Pi 5 secure-boot transaction without pretending those mutation, recovery, or verification operations exist in production.

A

Live preflight boundary

The existing tool can identify one lane-bound Pi 5 and evaluate partial public observations. Its result never authorizes a write or establishes the full baseline.

B

Admission + preparation

Simulate station health, exclusive target binding, then close deferred OTP, EEPROM, storage, inventory, firmware, and debug checks before preparing the exact manifest.

C

Approved one-shot commit

After approval and bidirectional trust, re-identify the exact target on its exclusive RPIBOOT lane before durable intent, execute-once commit, and authoritative readback.

D

Owned-state proof matrix

Walk signed cold boot, owned readback, authorized recovery, mandatory post-recovery readback, wrong-key rejection, root-integrity enforcement, and anti-rollback checks.

E

Fail-closed recovery

Keep an uncertain one-way result in progress until reconciliation. Changed targets, mismatched readback, missing evidence, or failed tests lead to owned quarantine, with no reset after the simulated irreversible boundary.

F

Shared station interface

Run the same HTML, CSS, controller, and transport in the loopback kiosk and GitHub Pages. Pages traverses the generated mock graph and has no target privilege.

02 / Safety contract

A completed demo is a reviewed state path—not proof from hardware.

MODELED BY THE DEMO SIMULATED

What the interface rehearses

  • Station admission, one transaction, one lane, and one bound candidate
  • Deferred-baseline closure, a complete manifest, and independent approval
  • Commit-time RPIBOOT re-identification, one-shot commit, and direct readback
  • Owned recovery, repeated readback, and positive, negative, integrity, and rollback tests
  • Final-control approval and intent, one-shot apply, cold restart, direct readback, and retest
NEVER IMPLIED OUT OF SCOPE

What completion cannot establish

  • That any physical Pi was inspected, fused, updated, booted, or tested
  • Device authentication, remote attestation, or an inventory ownership change
  • Live signing, mutation, owned-device probing, recovery, or readback authority
  • A device-unique private key, certificate, or active production identity
  • Evidence that can be substituted for a real journal or hardware ceremony

03 / Secure-boot transaction

The simulated path ends at enrollment_ready.

The workflow specializes the platform-neutral security-foundation stage for a Pi 5. Production identity enrollment begins only after this handoff and is outside the demo.

01 SIMULATED

Admit + bind

Check station posture and services, create the transaction, claim one lane, and bind one candidate.

02 SIMULATED

Close baseline + prepare

Resolve every deferred precondition, signed artifact, recovery bundle, policy, and test plan.

03 SIMULATED

Approve + establish trust

Bind independent approval to the exact plan and authenticate both candidate and enrollment domain.

04 SIMULATED

Commit + read back

Re-identify the RPIBOOT target, export intent, execute once, and reconcile authoritative state.

05 SIMULATED

Prove the owned state

Cold-boot signed code, re-read after recovery, and exercise rejection, integrity, and rollback paths.

06 SIMULATED

Finalize + reconcile

Approve and journal final controls, apply once, cold restart, read back, retest, audit, and permit enrollment.

04 / Provisioning station

The station executes policy. It does not own fleet authority.

A dedicated station isolates physical target access and short-lived bootstrap capability from everyday operator and development machines.

CONTROLLED STATION

One operator. One lane. One claimed target.

A generic orchestrator should enforce ordering, journaling, retry, approval, and postconditions while a pinned platform adapter performs hardware-specific work. A privileged lane guard exposes only the current target-facing interface.

! IMPLEMENTATION BOUNDARY

The ceremony is modeled. The mutation backend is not here yet.

The loopback kiosk and Pages demo render deterministic secure-boot states. They do not access USB, run the probe, handle secrets, authenticate operators or devices, contact control services or signers, program OTP, update EEPROM, boot hardware, or reconcile inventory. Interface parity does not imply production workflow authority.

Still required: a production Pi image and deterministic boot capsule, external signing, approved bundles, a mutating Pi 5 adapter and lane guard, an owned-device probe, persistent-root integrity and anti-rollback enforcement, recovery tooling, control and audit services, and physical positive, negative, power-loss, and quarantine tests.
